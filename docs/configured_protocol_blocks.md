# ブロック指定の状態・借用検証（実装済み）

`source-protocol-blocks.c.v1` は、compound block の `@verify(profile)` に
状態機械・持続借用の検査を適用する。

```c
void service(void) {
    struct transfer t;
    int buffer[4];
    transfer_init(&t);
    transfer_start(&t, buffer);
    // @verify(driver)
    {
        transfer_finish(&t);
    }
    buffer[0] = 1;
}
```

driver profile が対象 protocol を選択していれば、ブロック前の初期化・借用開始を
引き継いで完了を検査する。ブロック内で借用を開始した場合も、ブロックを出ただけでは
借用は消えず、後続処理のアクセスや関数終了時の整合性を検査する。
外部 operation とメモリアクセスの契約は従来どおり必要。

## 解析範囲

現在の実装は、状態・借用について囲んでいる関数全体を解析する保守的な方式。
ブロックだけを切り出して未知の入口状態を作ったり、借用を終了させたりしない。

- 関数冒頭からの状態・借用・別名・戻り値情報をブロックへ引き継ぐ。
- ブロック後も実際の状態を追跡し、早期 return、外側ローカルの寿命、ループの次周回を検査。
- 可視ヘルパーは本体を解析する。別翻訳単位や関数境界契約も既存の規則を適用。
- 状態を確立する前後の外部契約について、依存する外部前提・不確実性も出力し、受け入れ判定に含める。
- 前後を含む依存APIの許容文脈条件も検査する。文脈を指定した場合は文脈を保存する呼び出しモデルとして
  同じ文脈を用い、指定がなく必要なAPI文脈を確立できなければ未検証。
- 引数由来・構文などが未対応なら、囲む関数の解析で未検証となる。ブロック注釈で免除しない。

このため、ブロックに直接関係しないように見える外側の状態違反や未対応構文でも
検証を拒否する場合がある。ブロックのみの独立した証明や、必要最小限の依存範囲の抽出ではない。
複数の注釈付きブロックがあれば、それぞれの profile に対して囲む関数を検査する。

一方、`heap_allocate` / `block` / `wait` などの **禁止効果の適用範囲** は、
従来どおり指定ブロックとその呼び出し先。
例えば外側で wait を行ってからブロックに入り、ブロック内に wait がなければ、
ブロックの wait 禁止そのものには違反しない。
ただし、その外側 API の状態保存・アクセス・許容文脈などの契約は別途必要。
`@verify` は実行文脈を切り替える操作ではない。

## 結果レコード

各 obligation の file / firstLine / lastLine / symbol は指定ブロックを表す。
追加した `protocolScope` は、実際に状態・借用を解析した関数の symbol・file・行範囲と
`kind: "enclosing-function"` を記録する。
関数全体の指定は `kind: "function"`、protocol を選択しない効果専用検査では null。
診断が指定ブロック外にある場合も、実際の位置と関数の呼び出し経路を報告する。
`assumptions` にはブロックの前後に依存する外部前提も含む。
`effects` は指定ブロック側の効果集合であり、囲む関数全体の効果集合ではない。

正常系も外部モデルに依存する限り conditional。未受け入れの外部前提は gate を通過しない。
注釈だけで未検証な前後の操作を検証済みに昇格させない。

## 未対応範囲

ブロック専用の明示的な入出力契約、囲む関数から独立した境界証明、
未知の引数・グローバル・ヒープ由来、所有権解析との統合、IRQ/コールバックへの借用移譲、
動的な実行文脈切り替え、DMA の配置やキャッシュ・MMIO、資源・時間上限は未対応。
本機能で証明するのは、既存の状態・借用モデルの下での関数全体の整合性。
一般のメモリ安全性や実機ドライバ全体の保証を意味しない。

`python3 tests/run_tests_blocks.py` がブロック前後・早期 return・ループ・入れ子・別翻訳単位・
外部前提の欠落・外部APIの文脈制約を実 C と CLI で検査する。
仕様・フィクスチャは独自作成の架空 API。外部コード・資料の転載や依存追加はない。
