# 設定による実行文脈の検証（実装済み）

`--safety` の `source-contexts.c.v1` は、指定された実行文脈を直接呼び出しの
連鎖全体へ引き継ぎ、文脈ごとの禁止操作と API の呼び出し条件を検査する。
既存の効果解析を再利用するため、スカラーだけを扱うヘルパーや別翻訳単位の関数も対象。
文脈の名前は汎用の識別子であり、機種名や API 名を検査器に組み込まない。

## プロジェクトと外付け契約

```json
{
  "contexts": {
    "thread": {"forbid": []},
    "interrupt": {"forbid": ["heap_allocate", "block", "wait"]}
  },
  "profiles": {
    "handler": {"context": "interrupt"}
  }
}
```

これは project JSON 内の抜粋。`checks` または `@verify(handler)` で検証範囲を指定する。
関数・指定ブロックの入口文脈を要求として与え、同期的な呼び出し先まで伝播する。
本機能は、その入口が実機で割り込みとして登録されていることや、実際の IRQ 設定を証明しない。
結果レコードの `executionContext` は検証条件であり、ハードウェアから測定した事実ではない。

外付け functions 契約で、API が許容する文脈を明示する。

```json
{
  "symbol": "c:@F@configure_resource",
  "effects": [],
  "contexts": ["thread"],
  "assumption": "board.api.context"
}
```

`contexts` は完全な許容文脈の一覧。空配列、未知名、重複、型違いを拒否する。
実行文脈を検査する場合、外部 API の一覧が欠けていれば `MISSING_CONTEXT_CONTRACT`。
禁止された文脈の呼び出しは `FORBIDDEN_CONTEXT_CALL`。
API が文脈を要求しているのに検査側で文脈が指定されていなければ `MISSING_EXECUTION_CONTEXT`。
`effects: []` だけでは割り込みから呼べるという意味にはならない。
外部契約の assumption は引き続き報告され、受け入れても結果は conditional のまま。

文脈で禁止した効果と、profile 自体の `forbid` は和集合で適用する。
API を許容文脈に列挙しても、その API が持つ効果の禁止は解除されない。
例えば interrupt を許容する API に `heap_allocate` があれば、割り当て禁止の
文脈から呼んだ際に `FORBIDDEN_EFFECT` を検出する。
既知の割り当てプリミティブも従来どおり効果を隠せない。

`extends` で同名の文脈定義を合成すると禁止効果は和集合になる。
子設定で空の forbid を指定しても親の禁止は除去されない。
同名 profile の文脈を別名に変更する合成は競合として拒否する。
未知のキーや未対応の `contextSwitch` などを黙って無視しない。

## 呼び出し、本体との適合、結果

- 可視のヘルパーは現在の文脈で本体を解析し、契約を付けるだけで呼び出し先の検査を省略しない。
- 本体付き関数が許容文脈を宣言した場合、すべての宣言文脈で本体を検査する。
  選択された検証ルートから未使用でも、矛盾した契約は全体の受け入れを拒否する。
- 本体の禁止効果は `CONTRACT_CONTEXT_MISMATCH`、下流 API の文脈違反・欠落も診断する。
  本体を検査して適合した宣言だけを理由に、新たな外部前提を追加することはない。
- 間接呼び出し、未対応構文、未解決の効果は従来どおり未検証。
- 内側の `@verify` は追加の検証要求であり、外側から継承する実行文脈を変更しない。
- 既存の効果専用 profile と、文脈宣言のない外部契約は従来どおり利用できる。
  その場合、実行文脈を検証したとは報告しない。

JSON には文脈定義、各 obligation の入口文脈と合成した forbid、適用契約の許容文脈、
診断の文脈と呼び出し経路を含む。入力ハッシュ、コンパイル条件、四分類、終了コードも継続する。

## 対応範囲と未対応範囲

現在は一つの入口文脈を保ったままの呼び出し連鎖が対象。
外部 API の文脈契約は、その呼び出しが文脈を変更せず指定効果・許容条件に従うという外部前提を含む。
実際に割り込みマスクやスケジューラの状態を変更する API を、文脈保存 API として記載してはならない。
明示的な文脈切り替え、クリティカルセクションへの出入り、ロック保持による文脈変更、
コールバック・独立した割り込み入口への状態/借用移譲、再入可能性、共有データ競合、
atomic/メモリ順序や lock-free 検証はこの機能では証明しない。
既存のロック解析とは独立した軸であり、その解析の置き換えや統合完了ではない。

## 実行例とテスト

```sh
./kenbi --format=json --safety=demo/safety/context-thread.project.json
./kenbi --format=json --safety=demo/safety/context-interrupt.project.json
python3 tests/run_tests_contexts.py
```

同じ C ソースを通常文脈と割り込み文脈で検査する。
通常文脈の例は明示された外部前提の下で成立する。
割り込み文脈の例では共通のイベント処理は成立し、通常文脈専用の設定処理と待機処理は違反になる。
例・仕様・回帰テストは独自作成の架空 API。外部コードやベンダー仕様の転載、依存追加はない。
